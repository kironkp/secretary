Answering: “should the dashboard just be visual?”

Two surfaces, one secretary

Your instinct is right — but the axis isn't visual vs. interactive. It's what the AI has to touch to make a change. Touching data is instant. Touching markup is seconds. Touching code is minutes. So: keep the dashboard interactive (its changes were already instant), and add the thing you're actually describing — a page the secretary paints.

The real axis: what changes when you ask for a change

Dashboard instant

AI edits data — the LayoutPlan JSON. Hand-built components rearrange. Checkboxes, pins, revert all keep working because the AI never rewrites them; it repositions them. This is what we've specced.

Canvas seconds

AI writes markup — sanitized, script-free HTML it streams onto a page. Any shape it wants: posters, war-rooms, one big number. Click-to-expand only, provided by the app shell, never by the model. This is your “just visual” page.

New components minutes

AI writes code — the slow loop. Sandboxed, previewed, approved. The only tier where “redesigning the structures” happens, and the user never waits on it.

Feel the difference

Left: the Canvas repaints its whole shape per utterance. Right: the Dashboard applies data edits in place. Both are “talk → see it change” — different freedoms, different guarantees.

Why having both makes each better

The Canvas is the audition room. The registry is where auditions that keep getting called back become furniture.

This also answers the generatability problem quietly: coding agents are dramatically more reliable at generating a picture of your data than a stateful interactive widget. Letting new things be born visual is how the self-redesigning app stays trustworthy while it grows.
