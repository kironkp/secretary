Making the secretary's UI legitimately adaptive

Your idea — an AI that looks at the user's situation and reshapes the dashboard — is exactly where the industry landed in the last year. The research is unusually clear about which half of your idea to run at runtime and which half to run offline.

The one correction that makes it work

You proposed: designer AI writes a prompt → coding agent regenerates the UI. Google shipped exactly that (Gemini's generative UI) and reports a minute-plus per render, with output that beats markdown but still loses to human-designed layouts half the time. Anthropic built the same thing (Imagine with Claude) and shipped it as a five-day research demo, not a feature. Meanwhile Google's production answer for agent-driven interfaces — A2UI, now in Gemini Enterprise — does something different: the model emits a declarative JSON plan over a fixed catalog of components, and a dumb renderer executes it. Fast, safe, and still genuinely model-driven. So: keep both of your AIs — but only one of them runs while you're looking.

● Fast loop — every session (runtime)

A layout planner LLM reads your life-signals and emits a LayoutPlan JSON: which components, what order, what emphasis, and a user-visible why for every deviation. A deterministic renderer draws it. ~1 second, pennies, can't break the app — a bad plan fails validation and falls back to yesterday's.

● Slow loop — nightly/weekly (offline)

Your coding agent lives here. When the planner keeps wanting a component that doesn't exist, it logs a wishlist entry instead of improvising. The coding agent turns accumulated wishes into new components — versioned, previewed, approved by you — and the planner's vocabulary grows. The UI evolves; it just never mutates mid-use.

Why this split wins: the fast path is the A2UI/thesys pattern — model-driven composition with client-owned rendering, which is what survived contact with production. The slow path is where free-form code generation is actually good (no user waiting, human review, versioned artifacts). Latency ~1s vs ~60s+, and the failure mode is "default layout" instead of "broken app."

    What keeps it from being annoying
    
      
    Twenty years of adaptive-UI research compresses into six rules. Bake them into the planner prompt and the validator.
    
    
    
      
    
        
    0 · The Spreadsheet never adapts
    
        
    One surface stays a boring, complete, chronological ledger. When the dashboard reshapes itself, the user can always drop to the Spreadsheet and verify nothing was lost. Adaptation is only trustable when there's a non-adaptive floor under it.
    
        
    Why: trust in adaptive systems collapses when users can't audit what the adaptation hid.
    
      
    
      
    
        
    1 · Anchors are sacred, emphasis is free
    
        
    Tabs, search, and the section vocabulary never move. Within sections: accent, size, expand/collapse, inline detail — adapt freely, every render. Reordering sections needs a reason and is rate-limited to once a day (mornings are the natural boundary).
    
        
    Receipt: Findlater & McGrenere (CHI '09) — adaptive menus that move items degrade badly when predictions miss; spatially-stable adaptation degrades gracefully. Prediction accuracy is never 100%, so buy the graceful failure.
    
      
    
      
    
        
    2 · Confidence gates aggressiveness
    
        
    Weak signal → emphasis only. Strong signal → reordering allowed. A wrong accent costs the user nothing; a wrong rearrangement costs them their spatial memory of your app.
    
        
    Receipt: same study — at 50% prediction accuracy, moving-adaptations were slower than no adaptation at all.
    
      
    
      
    
        
    3 · Suggest-and-approve beats silent morphing
    
        
    Big reshapes arrive as a one-line offer: "You broke the album into 4 tracks — want the album card expanded into a tracker?" One tap. Small emphasis changes just happen.
    
        
    Receipt: Lavie & Meyer (IJHCS '10) — intermediate adaptivity (system proposes, user approves) beat full automation everywhere except perfectly routine tasks, and full automation degraded users' own skills.
    
      
    
      
    
        
    4 · Every deviation wears its why
    
        
    Each adapted section carries a chip: "Timeline first — you asked 3 schedule questions this morning." Your app's whole ethos is provenance on every fact; the layout is just another fact. It also makes bad guesses cheap to catch.
    
        
    Receipt: your own Aug 7 design decision — provenance on every captured item. This extends it to the frame itself.
    
      
    
      
    
        
    5 · Attention ≠ recolor
    
        
    Engagement emphasis = position, size, accent ring, inlined detail. Never a repaint: color keeps encoding deadline pressure, identity stays with the entity. (Also: highlighting alone measurably doesn't speed people up — pair it with size/position.)
    
        
    Receipt: Findlater — color highlighting showed no performance gain despite users liking it; and your palette already assigns color to pressure semantics.
    
      
    
      
    
        
    6 · Pin, revert, calm
    
        
    User can pin any section (a hard constraint fed back into the planner), revert to yesterday's layout, or switch to calm mode (the static default, forever). Measure reverts — a revert is a labeled wrong prediction, and it's your accuracy metric for free.
    
        
    Receipt: mixed-initiative principle — adaptation must be interruptible and reversible or users route around the whole feature.
    
      
    
    
    
  
    

  
  
    
    
    The planner prompt — paste-ready
    
      
    This is your "AI that feeds the other AI." Small/fast model, JSON output mode, temperature low. One call per dashboard open, cached on a hash of the signals.
    

    ## ROLE
You are the layout planner for a personal secretary dashboard. You never write
code or HTML. You emit exactly one LayoutPlan JSON object and nothing else.

## INPUT SIGNALS (precomputed by the app — you do not fetch anything)
projects[]     {id, name, kind, deadline, deadline_type: committed|inferred|none,
                days_left, open_count, done_count, subprojects[], momentum, people[]}
engagement     {project_id → mentions_24h, baseline_mentions, last_touched}
conversation   {today_topics[], schedule_word_share, questions_today[]}
pending        {items_missing_dates[], unanswered_asks[]}
calendar       {next_hard_commitment, days_to_it, density_14d}
context        {date, weekday, time_of_day, days_since_layout_change, pinned_sections[]}

## REGISTRY v1 — the only building blocks. Unknown components are rejected.
focus_banner   {text, tone: info|serious|critical}
hero_next_up   {event_id}
stat_row       {tiles[]: {value, label, tone?}}
project_card   {project_id, variant: full|compact|nested, accent?: bool, inline_loops?: bool}
timeline       {span_days: 14|21|35, expanded: bool}
open_loops     {group_by: project|date, include_done: bool}
date_chase     {item_ids[]}
people_index   {}

## HARD RULES (the validator enforces these too — violating them wastes the call)
1. Tabs, search, chrome: not yours. Never reference them.
2. pinned_sections keep their position and variant. Non-negotiable.
3. Reordering sections requires days_since_layout_change >= 1 AND a "why" on the
   moved section. Emphasis changes (variant/accent/expanded/inline_loops) are always allowed.
4. Any item with days_left <= 7 stays above the fold. Compact is fine; absent is not.
5. accent: true on at most ONE project_card. Accent means attention. Color always
   means deadline pressure — never reassign it.
6. Weak or ambiguous signal → emphasis only, no reordering. When torn, don't.
7. If the situation wants a component that doesn't exist, use the closest one and
   add a wishlist entry {need, closest_component, signals}. Never improvise structure.
8. Every section that deviates from DEFAULT_PLAN carries "why": one short sentence
   addressed to the user, naming the signal ("you asked 3 schedule questions today").
9. reason_summary: one line for the morning banner ("Reshaped for the album sprint").
10. On any doubt, emit DEFAULT_PLAN unchanged.

## DEFAULT_PLAN (also the fallback and the user's calm mode)
[hero_next_up, stat_row, project_card × each active (full), timeline(21d),
 open_loops(group_by: project), date_chase, people_index]

## OUTPUT
LayoutPlan JSON only. It must validate against LayoutPlan.schema.json.

    
  
    

  
  
    
    
    LayoutPlan — the contract between the two AIs and the renderer
    
      
    Small enough that a cheap model reliably emits it; strict enough that the renderer can't be surprised.
    

    {
  "plan_id": "2026-08-18-a",
  "reason_summary": "Timeline day — you were scheduling all morning",
  "sections": [
    { "component": "timeline",
      "props": { "span_days": 21, "expanded": true },
      "why": "You asked 3 schedule questions this morning" },
    { "component": "project_card",
      "props": { "project_id": "jazz-album", "variant": "compact" } }
  ],
  "wishlist": [
    { "need": "per-track progress bars inside the album card",
      "closest_component": "project_card variant:nested",
      "signals": "4 subprojects with own open/done counts since Aug 17" }
  ]
}

// Renderer contract:
//   unknown component or prop        → drop that section, log it
//   plan fails schema / rules 2–5    → render yesterday's plan, log it
//   model returns prose or markdown  → DEFAULT_PLAN
//   wishlist                         → append to wishlist.jsonl for the slow loop
// The model's output is DATA, never markup. Nothing it says reaches innerHTML.

    
  
    

  
  
    
    
    Build order
    
      
    Each version is useful on its own; each is one evening-sized step.
    
    
    
      
    v1
    
        
    Plumbing, no LLM — this weekend
    
        
    Build the registry + renderer + LayoutPlan format, but generate the plan from five hand-written rules (deadline ≤ 3d → accent that card; schedule_word_share > 0.3 → expand timeline; subprojects exist → nested variant…). You get 80% of the felt adaptivity, prove the plumbing, and this is the research-approved intermediate-adaptivity system already.
    
      
    
      
    v2
    
        
    Swap rules for the planner LLM
    
        
    One Haiku-class call on session open, JSON mode, cached on a signal hash so a quiet day costs zero calls. Add why-chips, the morning reason_summary banner, pin/revert/calm. Log every revert as a wrong prediction.
    
      
    
      
    v3
    
        
    The slow loop — your coding agent
    
        
    Nightly job: if wishlist has ≥3 entries for the same need, hand it + your design tokens + component source to the coding agent. It PRs a new component with a preview screenshot. You approve from the dashboard. Registry bumps, planner prompt gets the new block appended. This is the part that makes it legitimately adaptive — the vocabulary itself grows out of observed need.
    
      
    
      
    v4
    
        
    Optional: one-off generated views, sandboxed
    
        
    For explicit asks — "show me the album like a release war-room" — let the coding agent generate a full free-form view on demand, rendered in a sandboxed iframe, saved as an artifact. That's the Imagine-with-Claude / MCP-Apps end of the spectrum: fine as a special move the user invokes, wrong as the default dashboard.
